- **OIDC user auto-provisioning + group→role mapping + admin REST (P1-14 stage 3)** — Stage-2 produced a synthetic `RequestContext { userId: "oidc:<iss>:<sub>" }` from a verified JWT but never persisted that identity. Stage 3 closes that gap end-to-end: the first time a verified OIDC token reaches the server, an `OidcProvisioner` materializes a real user row + `oidc_identities` join row + group→role grants in one transaction, and every subsequent request from the same `(iss, sub)` resolves to that same `userId` instead of the synthetic placeholder. New drizzle migration `0016_oidc_provisioning.sql` (registered in `meta/_journal.json` idx=16) creates two tables: `oidc_identities` (PK `id`, FK `user_id` CASCADE, UNIQUE `(issuer, subject)` **globally** so a single SSO subject cannot be duped across tenants — issuer URL is already tenant-scoped in practice; `created_at` / `last_seen_at` for audit) and `oidc_group_role_map` (PK `id`, FK `role_id` CASCADE, UNIQUE `(tenant_id, group_name, role_id)` per-tenant so the same `engineering` group can map to different roles in different tenants without collision; `created_at` / `updated_at`). Two new repositories (`src/db/repositories/oidc-identity.repository.ts`, `oidc-group-role-map.repository.ts`) cover `findByIssuerSubject` / `findByUserId` / `create` / `touchLastSeen` and `findByTenantAndGroups` / `replaceForGroup` / `deleteById`. New `OidcProvisioner` core service (`src/auth/oidc-provisioner.ts`) is the heart of the change — `provisionFromJwt(payload, opts?) → {userId, tenantId, tags, isNewUser} | null`: returns null for non-string subject or missing `iss` (defensive — verifier already enforces this but provisioner must not assume); loads `oidc_identities` by `(iss, sub)`; on cache miss, generates a sentinel token `sha256("oidc-sentinel:" + randomBytes(32).hex)` (defends against collisions with real bearer tokens — opaque tokens never start with that prefix), inserts a new user row with `name = "oidc:<iss>:<sub>"` and that sentinel as `token`, then inserts the identity row. Race-safe path: if the identity insert raises a UNIQUE collision (parallel first-login of the same SSO subject), the provisioner soft-deletes the orphan user row it just created and returns the winner's `user_id` from the existing identity — both requests see the same userId, no duplicate users, no leaked sentinel. On every visit (new or returning) the provisioner: (a) touches `last_seen_at` for audit, (b) reads the JWT's `groups` (or custom `groupsClaim`), (c) joins via `oidc_group_role_map` to find roleIds for each matched group **filtered to the user's tenant** (mapping is tenant-scoped — `engineering` in tenant A grants different roles than `engineering` in tenant B), (d) **additively** merges those roleIds into `user_roles` (we ADD missing grants, never DELETE — preserves manually-granted out-of-band roles operators add via `user-role-cmd grant` so SSO doesn't stomp on them), (e) re-aggregates tags from the resulting role set and returns. `context-builder.ts` is now async on the OIDC path: `OidcContextOptions` gains an optional `provisioner?: OidcProvisioner` field; when wired, the verifier-success branch calls `await provisioner.provisionFromJwt(payload, {userClaim, groupsClaim})` and uses its `userId` / `tenantId` / `tags` instead of the synthetic placeholder. Tags from the provisioner are **unioned** with tags derived from the JWT's group claim (already in stage 2) — so an operator who has both DB role grants AND a JWT group claim sees both tag sources merged into one Set. Provisioner returning null OR throwing falls back to the synthetic context (network blip on a DB write must not invalidate an otherwise-valid token); the throw path additionally `oidc.logger.warn({reason: "oidc-provisioner-failed", err})` so ops can spot persistent DB failures. `AppDependencies` gains `oidcGroupRoleMapRepo` + `oidcIdentityRepo` fields wired **unconditionally** in `serve-cmd.ts` (admin REST works even when OIDC SSO itself is not configured — operators can pre-seed mappings before flipping the verifier on); `OidcProvisioner` is constructed only when `config.auth.oidc` is present (stays a true no-op when SSO is disabled). New admin REST surface (`src/http/handlers/admin/oidc.handler.ts`) registered in `app.ts`: `GET /api/admin/oidc/groups-mapping[?tenantId=]` lists all rows for the tenant (defaults `default`), `POST /api/admin/oidc/groups-mapping` `{groupName, roleId, tenantId?}` creates one mapping (201), `PUT /api/admin/oidc/groups-mapping` `{groupName, roleIds[], tenantId?}` atomic `replaceForGroup` (filters non-string / empty entries server-side so a malformed UI submission can't poison the row set), `DELETE /api/admin/oidc/groups-mapping/:id` (200 hit / 404 miss based on repo bool return), `GET /api/admin/oidc/identities?userId=` lists identity audit rows for one user. The handler early-returns when both repos are missing from `AppDependencies` — admin routes simply don't register, so a misconfigured deployment fails closed at the router rather than 500-ing on every call. 49 new unit tests across 5 files: `oidc-identity-repository.test.ts` 7 (find/create/touch/race), `oidc-group-role-map-repository.test.ts` 12 (CRUD + tenant scoping + atomic replace), `oidc-provisioner.test.ts` 10 (first-sight + idempotent + last-seen touch + group→role seed + non-mapped group ignore + additive merge with manual roles + custom claims + non-string filter + null-sub + missing-iss), `context-builder-oidc-provisioner.test.ts` 5 (real-userId resolution, null-fallback, throw-fallback, tag union, tenantId propagation), `admin-oidc-handler.test.ts` 15 (list/create/update/delete + validation + identity audit + deps-missing no-route registration). Regression 1471 → 1520 (+49). **Stage 4 deferred**: operator README sections (Chinese + English) covering IdP audience/claims setup + admin REST group→role configuration; integration tests against a real OIDC mock IdP (testcontainers Keycloak / dex). - **OIDC JWT verifier primitive (P1-14 stage 1)** — Cryptographic verifier primitive for SSO integration with Auth0 / Keycloak / Okta. New `JwtVerificationError` (`src/utils/errors.ts`) with 9-reason discriminator (`malformed` / `expired` / `not_yet_valid` / `invalid_signature` / `issuer_mismatch` / `audience_mismatch` / `key_not_found` / `unsupported_algorithm` / `jwks_fetch_failed`); all 9 reasons map to **HTTP 401** uniformly to defeat oracle attacks (an attacker probing the `/api/*` boundary cannot tell which check failed). New `OidcVerifier` (`src/auth/oidc-verifier.ts`) implements the full RFC 7519 / RFC 7515 verification pipeline using **Node 22 built-in `crypto.createPublicKey({format:"jwk"})` + `crypto.verify()` — no `jose` / `jsonwebtoken` / `jwks-rsa` dependencies** (zero supply-chain attack surface). RS256 default; RS384 / RS512 opt-in via `allowedAlgorithms`. Pipeline: split 3 segments → b64url decode → JSON.parse → validate `alg` ∈ allowed (HS* + `alg=none` explicitly rejected) → `RS_TO_HASH` map → fetch JWK by `kid` → `crypto.verify` → check `iss` strict-eq → check `aud` intersection (supports `string | string[]` config and `string | string[]` token claim) → check `exp`/`nbf` ± `clockSkewSec` (default 60s; both claims optional). New `IJwksProvider` interface + two implementations (`src/auth/jwks-provider.ts`): `RemoteJwksProvider` (TTL cache default 600_000ms, 5s `AbortController` fetch timeout, kid-miss triggers a single refresh to handle key rotation, second miss raises `key_not_found`, `inflight: Promise<void> \| null` deduplicates concurrent refreshes — prevents thundering herd when many tokens arrive simultaneously after TTL expiry; non-200 / malformed JSON / missing `keys` array → `jwks_fetch_failed`) and `StaticJwksProvider` (in-memory `Map<kid, Jwk>` for tests; both register a `__default__` alias for tokens without `kid` when the document holds exactly one key). New `auth.oidc?` optional zod block (`src/config/schema.ts`) with `issuer` / `audience` / `jwksUri` / `userClaim`=`sub` / `groupsClaim`=`groups` / `clockSkewSec`=60 / `jwksTtlMs`=600_000 / `allowedAlgorithms`=`["RS256"]`; absent triple disables SSO entirely (zero-config opt-in, behavior identical to pre-P1-14 builds). Env loaders in `src/config/index.ts` accept `OIDC_ISSUER` / `OIDC_AUDIENCE` (CSV multi-audience) / `OIDC_JWKS_URI` / `OIDC_USER_CLAIM` / `OIDC_GROUPS_CLAIM` / `OIDC_CLOCK_SKEW_SEC` / `OIDC_JWKS_TTL_MS` / `OIDC_ALLOWED_ALGORITHMS` (CSV). 28 new unit tests (`oidc-verifier.test.ts` 17 covering happy path RS256/aud-array/aud-allow-list + 14 failure modes including malformed segment count, non-base64url, unsupported HS256, `alg=none` forgery, kid not found, key-mismatch signature, payload tamper, iss mismatch, aud mismatch, expired beyond skew, accepted within skew, future nbf, no-exp/no-nbf accepted, custom RS512 algorithm; `jwks-provider.test.ts` 11 covering Static hit/single-key fallback/unknown-kid, Remote TTL cache hit + kid-miss rotation refresh + 2nd-miss `key_not_found` + TTL expiry refetch + non-200/non-JSON/missing-keys → `jwks_fetch_failed` + concurrent dedup); regression 1424 → 1452 (+28). **Stages 2/3/4 deferred**: stage 2 — auth middleware wiring detecting 3-segment JWT in bearer header, attempt OIDC verify, fall back to opaque sha256 lookup; stage 3 — user auto-provision on first OIDC token + group→role mapping table; stage 4 — admin REST `GET/PUT /api/admin/oidc/groups-mapping` + operator docs. See `docs/ARCHITECTURE.md` §12 batch 41.
